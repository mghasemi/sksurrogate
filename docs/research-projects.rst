==================
Research projects
==================

The API provides a small metadata workspace for grouping research questions,
notes, research records, and references to existing SKSurrogate artifacts.
Projects do not copy datasets, bundles, or full job outputs; they retain
bounded provenance snapshots of linked artifacts. Projects do not replace
``mltrack``, the job store, or the model registry.

Create a project
================

Create a project and link an existing registered dataset partition::

    curl -X POST http://127.0.0.1:8013/api/projects \
      -H 'Content-Type: application/json' \
      -d '{
        "name": "Material degradation",
        "description": "Investigate operating conditions and degradation.",
        "research_questions": [
          "Does temperature affect degradation?",
          "Is the relationship nonlinear?"
        ],
        "artifacts": [
          {
            "kind": "dataset_partition",
            "task_name": "degradation-pilot",
            "artifact_id": "train",
            "label": "Pilot training partition"
          }
        ]
      }'

The API returns a generated ``project_id``, timestamps, empty notes, the
questions, and the linked-artifact references. Project IDs are generated by
the API and are not caller-selected.

Artifact references
===================

Projects accept references to:

* ``dataset_partition`` — ``artifact_id`` is a registered partition name.
  The task's stored partition metadata is checked when the reference is saved.
* ``model_bundle`` — ``artifact_id`` is a model version in the task's bundle or
  registry directory. Use the existing run-configuration and Markdown-report
  endpoints to inspect its reproducibility record.
* ``job`` — ``artifact_id`` is a background job ID belonging to the same task.
  Use ``GET /api/jobs/{job_id}`` for its recorded request, current status, and
  result. In the web UI, **Inspect job** opens its tracker and result on the
  Jobs page. For example, nested-CV jobs retain the submitted evaluation settings
  alongside result-level partition fingerprints and metrics.
  Sensitivity-analysis jobs likewise retain their method request and result
  protocol, including the registered input-partition fingerprint, row count,
  and feature columns.
* ``reference`` — an external citation. The shape is ``{"kind": "reference",
  "url": "https://…", "title": "…", "doi": "…", "label": "…"}``; only ``url``
  is required, it must be an absolute ``http(s)`` URL of at most 2,048
  characters, and the API **never fetches it**. References are deduplicated by
  URL and do not carry ``task_name``/``artifact_id``.

References are validated on project creation and update. To append one
reference without replacing project fields or other artifact links, use
``POST /api/projects/{project_id}/artifacts`` with one artifact reference as
the request body. This append operation is idempotent for an already-linked
artifact identity. A snapshot is captured when a reference is first linked
and preserved by later project edits; it is never re-baselined, so the stored
snapshot always describes what was observed at link time rather than the
current upstream state.
Dataset snapshots include the registered partition fingerprint and schema
metadata (ingestion timestamp, row count, columns, target, feature count);
bundle snapshots include run identity, lineage, configuration, and
dependencies; job snapshots fingerprint their recorded configuration and, when
a result is present at link time, its content. ``GET
/api/projects/{project_id}/summary`` reports each linked artifact with a
``snapshot_status``:

* ``current`` — the artifact still exists and recomputes to exactly the
  fingerprint captured at link time.
* ``changed`` — the artifact exists but no longer matches its snapshot: the
  partition was re-registered under the same name, the bundle's run
  configuration changed, or a job result appeared after the reference was
  linked (job status transitions do not alter the fingerprint; only recorded
  configuration and result content do).
* ``missing`` — the upstream artifact no longer exists: the task's mltrace
  database file or the named partition is gone, the bundle file is absent from
  both the task's bundle directory and the registry, or the job record was
  deleted.
* ``unverified`` — the artifact exists but the project record carries no
  stored snapshot (a legacy record created before snapshots were captured).

External references are project metadata, not stored artifacts. Their snapshot
uses schema ``sksurrogate.project-artifact-snapshot.v2`` and records the stored
fields only (``url``, ``title``, ``doi``) with ``content_embedded: false``; it
never contains fetched page content. Because reachability is never checked, the
summary status of a reference is always ``unverified`` — that is the honest
state, not a transient one. Linking a reference does not advance any workflow
stage (the checklist still follows partitions, bundles, and jobs), but a
reference linked to the project may satisfy the evidence requirement of a
finding or conclusion. For example, appending one reference::

    curl -X POST http://127.0.0.1:8013/api/projects/PROJECT_ID/artifacts \
      -H 'Content-Type: application/json' \
      -d '{"kind":"reference","url":"https://doi.org/10.1000/xyz",
           "title":"Controlled yield study","doi":"10.1000/xyz"}'

Snapshots identify what was observed but do not freeze or copy the upstream
artifact; a deleted artifact cannot be recovered from project metadata, and
there is no supported way to reset drift on an existing reference. In
particular, an artifact cited as evidence in a research record cannot be
removed through ``PUT`` (see Research records and evidence below). Durability
is a property of the upstream stores rather than of project metadata:
partition rows live in the task's mltrace database (``mltrace/<task>.db``),
bundles under ``bundles/`` and ``registry/``, and job records as JSON files
under ``jobs/`` in the configured API storage root. Back up those directories
to keep linked artifacts recoverable; project files alone do not suffice.
References with unsupported path characters, duplicate references, or
mismatched task/job pairs are rejected.

The summary tracks the research progression: a project question, hypothesis,
registered dataset, completed analysis, completed modeling run, available
result, and recorded conclusion. Question and record stages reflect project
metadata; data, analysis, modeling, and result stages reflect linked artifacts.
The analysis stage is complete when a linked ``sensitivity`` or ``nested-cv``
job has completed. The modeling stage is complete only when a linked
``experiment``, ``optimize_pipeline``, or ``retraining`` job has completed;
completed analysis jobs do not count as model-training progress. A result is
available when a linked job completes with a non-null result or a model bundle
is linked; a completed job without a recorded result does not satisfy this step.

Questions and notes
===================

Use ``GET /api/projects`` to list project records and
``GET /api/projects/{project_id}`` to retrieve one. ``PUT
/api/projects/{project_id}`` replaces its name, description, questions, and
artifact references; its creation time and existing notes are preserved.

Append an observation with ``POST /api/projects/{project_id}/notes``::

    curl -X POST http://127.0.0.1:8013/api/projects/PROJECT_ID/notes \
      -H 'Content-Type: application/json' \
      -d '{"text": "The pilot suggests an interaction worth testing."}'

Each note receives its own ID and creation timestamp. The web UI's **Projects**
page can create projects, show their progress, link available artifacts,
append notes, and add research records. **Register data**, **Run an analysis**,
and **Run an experiment** carry the project context to their respective pages.
A successfully registered partition is automatically linked to the project.
Completed sensitivity, experiment, and pipeline-optimization jobs launched
in that context are automatically linked through the additive artifact
endpoint; failed or unfinished jobs are not. When a completed modeling job
returns a ``model_version``, its produced bundle is linked as well. Other jobs
can be linked from the Projects page after completion. Linked job
evidence has an **Inspect job** link to open its tracker and result. Evidence
in saved records also shows whether its linked artifact snapshot is current,
changed, missing, or unverified. Projects do not yet support notebook
execution, project deletion, or project-level report generation.
Authorization is limited to the API's existing optional API-key middleware.
Project records
are stored as JSON under the configured API storage root; deployments should
use a single API process for writes, as the file store is not a distributed
multi-worker database. Deployment, registry, monitoring, and retraining remain
separate operational workflows.

Research records and evidence
=============================

Append a hypothesis, analysis, finding, or conclusion with
``POST /api/projects/{project_id}/records``. Records are append-only and have
their own IDs and timestamps. Findings and conclusions require at least one
evidence reference; hypotheses and analysis notes may be recorded before
evidence is linked. Evidence must point to an artifact already linked to the
project and is labeled as supporting or contradicting. Hypotheses start in
``proposed`` status and may move among ``proposed``,
``under_investigation``, ``supported``, ``contradicted``, and ``inconclusive``.
Each transition is appended to ``status_history`` and does not rewrite the
hypothesis text or its evidence. A hypothesis may optionally cite one of the
project's research questions using the ``research_question`` field; the
captured question text remains with the hypothesis. Change a hypothesis status with
``POST /api/projects/{project_id}/records/{record_id}/status``::

    curl -X POST http://127.0.0.1:8013/api/projects/PROJECT_ID/records \
      -H 'Content-Type: application/json' \
      -d '{
        "kind": "finding",
        "title": "The pilot result is inconclusive",
        "text": "The registered data and fitted bundle give conflicting indications.",
        "evidence": [
          {
            "relation": "supports",
            "artifact": {
              "kind": "dataset_partition",
              "task_name": "degradation-pilot",
              "artifact_id": "train"
            }
          },
          {
            "relation": "contradicts",
            "artifact": {
              "kind": "model_bundle",
              "task_name": "degradation-pilot",
              "artifact_id": "baseline-v1"
            }
          }
        ]
      }'

    curl -X POST http://127.0.0.1:8013/api/projects/PROJECT_ID/records/RECORD_ID/status \
      -H 'Content-Type: application/json' \
      -d '{"status": "under_investigation"}'

Existing hypotheses created before status tracking are presented as
``proposed``; that default is anchored to the record's original creation time.
Each record can include up to 20 evidence references, and a project can contain
up to 1,000 records. The Projects page supports multiple evidence references
and lets each be labeled independently. Evidence may be added after a record
is created with ``POST
/api/projects/{project_id}/records/{record_id}/evidence``. Evidence is
append-only; the referenced artifact must already be linked to the project,
and duplicate relation/artifact pairs are rejected.

The project metadata stores references and claims, not copies of dataset,
job, or bundle contents. An artifact used as evidence cannot be removed from
the project through ``PUT``; remove or revise dependent records through a future
versioned record-management API before changing that relationship. The Projects
UI is a bounded record workspace rather than a full workflow orchestrator;
record editing/deletion and rerunning analyses from project records are not
provided.

LLM-assisted synthesis (opt-in)
===============================

Projects can draft a short, **cited** note from already computed artifacts. The
feature is disabled unless the API process is configured with a user-supplied,
OpenAI-compatible chat-completions endpoint; it adds no package dependency and
never receives raw dataset rows. See :doc:`controlplane` for the environment
variables.

Submit a synthesis job with ``POST /api/synthesis/projects/{project_id}``::

    curl -X POST http://127.0.0.1:8013/api/synthesis/projects/PROJECT_ID \
      -H 'Content-Type: application/json' \
      -d '{"task_name":"diabetes","model_version":"VERSION",
           "job_id":"JOB_ID", "include_explanations":true,
           "include_drift":false}'

The job returns ``draft`` (text, citations, word count), ``sources``
(id/kind/label), ``computed_facts`` (the exact aggregate payload sent to the
provider), ``provider`` metadata, and an ``interpretation`` block labelled
``generated_interpretation`` with ``causal_effect: false``. ``GET
/api/synthesis/status`` reports whether a provider is configured without
echoing credentials.

**Sources and data handling.** Facts are aggregated from stored artifacts:
``S1`` dataset profile (counts, column kinds/missingness, top target
associations, quality flags), ``S2`` an optional job's whitelisted
configuration and scalar metrics, ``S3`` bundle metadata, ``S4`` explanation
summaries (importance means and ALE ranges), and ``S5`` recent stored monitoring
alerts. Raw rows, file paths, model objects, and credentials are never sent.
The prompt is not stored; the job result and any saved note follow the normal
jobs/notes retention rules, and the operator owns the provider's retention
behaviour.

**Citation contract.** The system prompt requires a ``[S1]``-style citation for
every factual sentence. A draft that is empty, longer than 6,000 characters,
cites nothing, or cites an id that was not supplied fails the job with a named
reason; it is never accepted silently.

**Saving a draft.** Synthesis does not modify the project. Persisting is an
explicit note action with provenance::

    curl -X POST http://127.0.0.1:8013/api/projects/PROJECT_ID/notes \
      -H 'Content-Type: application/json' \
      -d '{"text":"... [S1] ...", "source":"generated",
           "model":"MODEL", "citations":["S1"],
           "computed_facts":[{"id":"S1","kind":"dataset_profile","data":{...}}],
           "synthesis_job_id":"JOB_ID"}'

Generated notes are rejected without a model id or citations, with citations
that do not match a supplied fact, or with computed facts above 30,000
characters. Human notes remain unchanged apart from a ``source: "human"``
field, and all notes stay append-only. The generated prose is model
interpretation, not a computed result: verify it against the stored computed
facts, and do not read citations as evidence of causality.
