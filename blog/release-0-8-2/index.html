SKSurrogate 0.8.2: what ships, what it does not, and how to check

Version 0.8.2 is on PyPI, on Docker Hub and in the Zenodo archive. It is a correctness release rather than a feature release, which makes it the right moment to state plainly what the thing does, what it loses, and how you can verify all of it without trusting me.

Mehdi Ghasemi · 27 November 2026 · release

SKSurrogate is a surrogate-optimization toolkit built on scikit-learn. The tuner is a BaseSearchCV subclass, so it drops into existing code with the same fit/predict contract as GridSearchCV and RandomizedSearchCV, and it replaces BayesSearchCV — whose upstream, scikit-optimize, is archived and no longer imports against current scikit-learn. Everything else in the project exists to make the result checkable: a dataset fingerprint, the protocol, the seeds, and the evaluation record travel with every number.

What is in this release

The search loop is now reproducible at a fixed random_state. Two things used to break that: the start point was drawn from the global random.uniform, so every run began elsewhere, and candidate estimators carried grid hyperparameters but no random_state, so an unseeded forest scored differently each time and the selection flipped. On the regression notebook search, the same seed previously gave RMSE 18.9 and 20.3 for the same candidate. Both sources are now derived from the seed you pass.

Three fixes came out of writing the example notebooks, which is the useful part of the story: data diagnostics no longer crash on a grouping column with unlabelled rows (they are excluded and counted instead); regression learning curves are scored with a regression measure rather than being silently replaced by accuracy, which had produced all-NaN curves; and forecast metrics survive gaps in the history instead of turning an entire series' MASE into NaN.

The three end-to-end notebooks — classification, regression, time series — pin their seeds and treat the evaluation budget as the binding constraint, so their numbers are reproducible rather than illustrative. They ship in the repository and in the sksurrogate-lab image; they are not in the wheel. Full notes: changelog 0.8.2.

What it does not do

This table is the reason to read the post. Every entry is measured in the project's own published studies, and the raw runs are archived with a DOI.

Claim you might expectWhat the evidence says
Beats Optuna-TPE on accuracyNo. At an equal evaluation budget TPE is top on 5 of 6 datasets, and the methods sit within about half a point of each other.
Beats portfolio AutoMLNo. FLAML is ahead on 5 of 6 datasets at an equal wall-clock cap, AutoGluon on 3 of 6. The dataset means differ by 0.40 pt, which the study calls within its own noise floor.
Is cheap to runIt is not. At a 120-second cap, 49 % of the budget is search overhead — 22 % fitting the surface, 27 % in the acquisition optimiser — and per-fit cost grows from 3 ms to 174 ms as the surface fills.
Reaches a target fasterNot reliably. Uniform random search is fastest to a 1 % gap on four of six datasets at this budget.
Wins at a larger budgetNot tested. The B=60 extension compares response surfaces against each other; there is no Optuna arm at B=60.
Ships a web UI in pip installNo. The wheel contains SKSurrogate and sksurrogate_mcp; the control plane is a container.

What is real

Final quality under an equal evaluation budget, and fewer evaluations to get there: median 21.5 evaluations to a 1 % gap versus 55.0 for random search on the same 1,220-pipeline space, buying a median 281 candidates against 553. The response surface is what carries it — the default RBF-GP beat the older cubic Hilbert surface on all six datasets at both budgets (20W/17T/5L at B=30, p ≈ 4×10⁻³), and an untuned KernelRidge surface is worse than fitting nothing once the guidance window opens. One of the study's findings is a defect in this project's own encoding: the ordinal surface was masking the advantage, and replacing it with a mixed-categorical one lifted best-CV by at least 0.3 pt in four of six datasets.

That is the case for the tool: not faster, not more accurate, but evaluation-efficient and honest about where it is neither. If you want plain hyperparameter tuning and nothing else, use Optuna.

How to check it in five minutes

Nothing below requires trusting this page.

pip install sksurrogate==0.8.2

# a seeded search: same random_state, same trials, same winner
python -c "import SKSurrogate; print(SKSurrogate.__version__)"

# reproduce the benchmark tables from the archived raw runs
python -m benchmarks.run --dataset all --budget 30

What I want from you

Most of the useful changes in this release came from running the thing on real data and finding that a column with missing labels crashed a diagnostic. The same will be true of whatever you run it on.

So the ask is specific: run one notebook, and tell me where it breaks — or where a number disagrees with the published table. The issue forms now require the fields that make a report actionable: the version, the random_state, and for a benchmark disagreement the budget currency, the exact command and a link to your raw output. A reproducible disagreement is a contribution, not an argument.
